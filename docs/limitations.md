# 既知の限界

このシステムは「元レシピの曖昧さ」と「LLM の挙動」という、本質的に避けられない不確実性の上に成り立っている。ここではその境界を率直に書き出す。設計判断や残課題は [Open Issues](https://github.com/chai0204/recipe-optimizer/issues) を併読のこと。

---

## 1. 元レシピの曖昧さ

家庭料理レシピは「人間が人間に伝える」前提で書かれており、機械可読性は最初から想定されていない。具体的に以下が常に発生する。

### 1.1 量の表現が物理量にならない

| 元表現 | パーサが補完する必要 |
|---|---|
| 「適量」「お好みで」 | 数値化不可。pipeline は無視 |
| 「少々」「ひとつまみ」 | 経験的に 1-2g 程度に推定するしかない |
| 「●しょうゆ 大さじ1」 | 単位は機械可読だが「●」のようなグルーピング記法は parser 依存 |

→ `Ingredient.quantity_text` は **生文字列のまま** 保持する設計。構造化を試みると失敗が連鎖するため。

### 1.2 時間の曖昧さ

| 元表現 | 実際 |
|---|---|
| 「煮込む」 | 10-15分のレンジ。レシピや具材に依存 |
| 「半熟になるまで」 | 視覚判断。秒～分のばらつき |
| 「香りが立つまで」 | 嗅覚判断。LLM は 30秒～1分と推定する傾向 |
| 「よく混ぜる」 | 物理量なし |

→ Haiku は妥当な推定値を出すが、Q4_K_M 級のローカル LLM は 1.0min のデフォルトに落ちる傾向。`scheduler.makespan` は本質的に **概算** であって、実時間は ±30% の幅で動く。

### 1.3 火加減・温度

「中火」「弱火」「強めの中火」は物理量と一意に対応しない。`ProcessEdge.parameters` に `heat_level: "medium-high"` のような文字列を保持するが、scheduler はこれを利用しない（する根拠がない）。

### 1.4 暗黙のステップ

元レシピが「切った鶏肉を加える」とだけ書いて chop 工程を省略している場合、parser はそれを補う責任を負う。Haiku はこれをかなり安定してこなすが、ローカル LLM は補完を忘れることがある。

## 2. LLM の挙動限界

### 2.1 同じ入力でも出力がぶれる

各バックエンドの `LLMCallContext.temperature = 0.0` 既定でも、サンプリング過程の数値誤差で出力が微妙に変わる。

Haiku 4.5 で同じ親子丼を 3 回流すと:
- ノード数: 11 / 15 / 12 でぶれる
- 調味料の扱い: 個別 mix vs まとめて 1 ノード
- ノード命名: `n_chicken_diced` vs `n_chicken_cut` vs `n_chicken_pieces`

scheduler / checker は ID 参照で動くため動作上の問題はないが、**「再現性のあるテストケース」を組むには手作り fixture を使う方が安全**。

### 2.2 量子化のクオリティ・クリフ

GGUF Q4_K_M Gemma-4-E4B での観察結果:

| 項目 | Q4_K_M (few-shot 1件) | Haiku 4.5 |
|---|---|---|
| action 正しく選ぶ | ✓（few-shot 付与後） | ✓ |
| `hold_duration_min` | 5.0（cook と burner で同値、区別できない） | 1.0 vs 4.0（区別） |
| `name_hint` 抽出 | None（生レシピ中の「やかん」を拾えない） | 「やかん」抽出 |
| `is_final=True` 設定 | 未設定 | ✓ |

→ Q4_K_M は **「スケジュール可能な valid 構造」** までは到達するが、内容の精度は Haiku に大きく劣る。Q6_K や Q8_0 で改善する見込みだがメモリ・推論時間も増える。

### 2.3 不在領域での LLM フォールバックが暴走する

`tool_use_table.json` にない action を proposer が解決しようとすると LLM フォールバックが発火する。Q4 / Haiku どちらでも、**「ありそうな代替」を即興で作る** 傾向があり、物理的に成立しない結果になり得る:

- 冷蔵庫 → 「片手鍋で蒸らす」（鍋では冷却不可、Issue #10）
- 圧力鍋 → 「電子レンジで圧力調理」（無理）

table をシード時点で網羅しておくか、生成された option に semantic verifier を通す（Issue #10 step 2）か、`Resource.substitutable: bool` でフラグ化する（step 3）かが対策。

### 2.4 推定 duration が現実とずれる

特に prep 系で観察:
- 「鶏肉を一口大に切る」を Haiku が **5分** と推定するケース（実際は 2分前後）
- 「卵を溶く」を **1分** と推定（妥当）
- 「玉ねぎを薄切りにする」を **3-5分** と推定（妥当）

長めの推定はユーザーの安心感には繋がるが、**makespan の累計が膨らむ**ため UX を圧迫する。`UserProfile.skill_factors` で補正する設計はあるが scheduler への注入は未実装（Issue #5）。

### 2.5 構造化出力強制の限界

GGUF バックエンドは llama.cpp の grammar 制約で **JSON 形が正しいこと** は強制できる。だが grammar は意味的整合性（「container kind なのに `name_hint=水`」のような誤り）までは保証しない。Pydantic validator がカバーする範囲も型レベルに限られる。

## 3. 代替の semantic gap

### 3.1 容器の継続使用が考慮されない

mugicha レシピで:
- step 1: 片手鍋で湯を沸かす
- step 2: 「やかんに麦茶パックを入れ蒸らす」← パーサは container=やかん で記述

ユーザーは step 2 で **step 1 と同じ片手鍋** をそのまま使い続けるのが自然だが、proposer は前段のリソース選択を見ないので、`rest` action の候補から無関係な「氷水で急冷」が選ばれることがある。これは [Issue #4](https://github.com/chai0204/recipe-optimizer/issues/4) として記録。

### 3.2 「同じ action」の中で sub-context が違う

`mix` というアクションは「ボウルで卵を混ぜる」「鍋で具材を加える」「フライパンで炒め合わせる」など多くの sub-context を持つ。テーブルは全部「ボウル+菜箸」「ボウル+泡立て器」を提示するため、麦茶の e_brew（鍋で麦茶パックを加える）が「ボウル+菜箸」に置換される、といった文脈崩壊が起きる。

→ action enum を `mix_in_bowl` / `mix_in_pot` のように細分化すると改善するが、enum 拡張は壁が大きい。

## 4. リソースモデルの粗さ

### 4.1 workstation 抽象化

「包丁＋まな板」を `workstation` 1スロットとして扱う。実際にはまな板が複数あれば prep を並列化できるが、PoC では workstation_count=1 で固定し細分化しない。

### 4.2 BURNER 内のサブ区分なし

ガスコンロ / IH / 魚焼きグリル / 中華レンジを `BURNER` 1 つで扱う。実プロダクトでは「ガスでないと困るレシピ」「グリルでないと焼けない魚」のような細粒な要求が出てくるが、現状の attributes は scheduler から参照していない（Issue #6 はクローズしたが、内部攻略は未実装）。

### 4.3 ユーティリティの contention 未考慮

包丁・菜箸・おたまなどの utensil は「短時間で他に貸し借りされる」前提で、scheduler は contention を計算しない。複数人で同じキッチンを使う場合は穴が出る。

## 5. スケジューラの想定

### 5.1 Greedy list scheduling

リソース制約付きの完全最適化（RCPSP）は NP-hard なので、scheduler は topological order × earliest-fit の greedy 解法。**局所最適**であって全体最適ではない。意図的にエッジを並べ替えれば makespan を 5-10% 改善できる場合があるが、PoC では十分。

### 5.2 静的レシピ前提

「卵を落とした」「玉ねぎを切り終わるのが早かった」のような **dynamic state 更新** は対象外。レシピ生成フェーズの設計であり、ライブ実行モード（フェーズ B）の責務。

### 5.3 待ち時間を最大活用する設計

`hold_duration_min < duration_min` のエッジ（煮込み中で cook が解放される等）を見つけたら、そこに別エッジの cook 拘束を差し込む。これは並列化の本領だが、**「人間が実際にそれをできるか」** は別問題。煮込み中に切ることは普通だが、煮込み中に揚げ物をするのは現実的でない、といった粒度の経験則は持たない。

---

## 6. クリティカルパスの解釈

`Schedule.critical_path_edge_ids` は **リソース無限仮定** の longest dependency chain。実際の makespan は CP の 1-2 倍になる（cook の serialization 等のため）。

ユーザーに「最低◯◯分」と提示すると、「思ったより時間がかかる」となりがち。実装上は `total_duration_min`（実測値）を主に出している。CP は内部分析と UI の "earliest possible" 表示用。

## 7. 経済的限界

### 7.1 LLM 呼び出しコスト

`claude -p` 経由の Haiku 4.5 は 1 呼び出し約 $0.15-0.30（Claude Code のシステムプロンプトを毎回ロードするため）。parser + renderer の opt-in で **約 $0.30-0.60 / レシピ** になる。

本番運用するなら:
- Anthropic Messages API を直接叩く（tool_use で structured output、システムプロンプト最小化）
- もしくは OpenAI / 他社 API
- もしくはローカル GGUF（Q6 / Q8 でクオリティを許容範囲に）

PoC スコープではこの最適化は対象外。

### 7.2 GGUF ロード時間

CPU で 4-5GB GGUF をメモリにロードするのに **3-5秒**。1-shot 起動だと許容範囲だが、サーバとして常駐させたい場合はモデル load を1回に。

## 8. これは「直せない」と思っていること

| 項目 | 理由 |
|---|---|
| レシピ毎の duration_min ばらつき | LLM の確率的サンプリングの本性。retry / averaging で緩和は可能だがコスト増 |
| 「適量」の数値化 | 元レシピが意図的に曖昧。AI が決め打つと「料理人の自由度を奪う」 |
| 文脈崩壊（同 action 内の sub-context） | action enum を細粒化しない限り根本解決しない。コスト/影響のトレードオフ |
| 物理的に成立しない代替（冷蔵庫→鍋） | LLM フォールバックの本性。verifier を入れない限り発生し続ける |

これらは「PoC として無理に解こうとしない」境界として扱う。プロダクト化する時に対処する。
